# Change Log

## 2026-06-05

### 변경 내용

- 제품 설명을 입력형 워크플로우 앱이 아니라 Codex 작업 관제판 방향으로 정리했다.
- 홈 체크리스트 영역을 최근 수정 패널로 교체하고, 자동 생성 상태 파일은 최근 수정 목록에서 제외했다.
- 핵심 문서 원문, 기능별 spec 상태, 작업 진행률, 최근 수정 파일이 새로고침마다 반영되도록 상태 동기화 흐름을 정리했다.

### 변경 이유

- 비개발자가 직접 체크리스트를 관리하거나 프롬프트 생성 버튼을 누르는 흐름보다, Codex 작업 중 현재 프로젝트 상태를 옆에서 확인하는 관제판 역할이 실제 사용 목적에 더 맞다.

### 테스트 결과

- `./scripts/run_tests.sh` 통과.
- 인앱 브라우저에서 최근 수정 패널, 문서 패널 테두리, 단계 카드 진행률 하단 정렬을 확인했다.

### 남은 작업

- 기능 추가는 보류하고, README와 상태 동기화 기준을 유지하며 실제 사용 중 필요한 개선만 후속 검토한다.

### 변경 이유

- 상단 버튼이 현재 단계 탐색보다 강하게 보여 사용자가 문서/단계 흐름을 읽는 데 방해가 됐다.
- Stitch 3차 화면의 큰 타이포그래피가 실제 앱에서는 정보 밀도를 떨어뜨려 한 화면에서 진행 상태를 보기 어렵게 만들었다.
- ADR-0001의 로컬 우선 정적 앱 결정을 유지하면서 디자인 일관성을 높여야 한다.
- 현재 단계에서는 동적 데이터 연동보다 비개발자가 흐름과 상태를 읽기 쉬운 정적 시각화 품질을 먼저 높이는 것이 안전하다.
- 작업 화면은 사용자가 어떤 기능의 어떤 작업을 진행 중인지 시각적으로 추적할 수 있어야 하므로, 기능과 태스크 간 연결선이 필요하다.
- 태스크 맵은 상세 설명보다 전체 방향과 연결 관계를 빠르게 읽는 화면이어야 한다.
- 마인드맵 연결선은 개별 카드보다 관계를 먼저 인식하게 해야 하므로 선의 연속성이 중요하다.
- 홈 화면은 상세 작업보다 현재 상태와 다음 단계를 먼저 판단할 수 있어야 한다.
- 문서 생성 현황은 많은 문서를 빠르게 훑을 수 있도록 카드형 그리드보다 한 줄 리스트가 적합하다.
- 홈에서 실제 작업의 중심은 칸반 보드이므로, 단계/문서/체크리스트는 보조 정보로 축소되어야 한다.
- 칸반 컬럼 상태는 작업 판단의 핵심 신호이므로 제목에 색상 강조가 필요하다.
- 단계 카드, 체크리스트, 문서 현황은 보조 정보지만 실제 진행 개수와 화면 표시 개수가 어긋나면 사용자가 상태를 오해할 수 있다.
- 칸반 컬럼 제목은 상태 판단용 라벨이므로 좁은 컬럼에서도 가로 pill 형태를 유지해야 한다.
- 단계 카드는 홈 상단의 보조 상태 요약이므로 강한 배경색보다 간결한 카드와 진행률 바가 전체 화면과 더 잘 어울린다.
- 계획 화면은 문서 종류별 분리보다 기능 단위의 진행 상태를 먼저 보여줘야 사용자가 어떤 기능이 어디까지 준비됐는지 빠르게 판단할 수 있다.
- 기능 카드는 실제 템플릿 문서 구조와 연결되어야 하므로 임의의 `F-001` 코드보다 `specs/<feature-name>/` 경로 표시가 더 명확하다.
- 제품 전체 spec과 기능별 spec을 분리해야 이후 기능 구현, 검증, 변경 로그가 실제 템플릿 흐름과 일치한다.
- 경로는 이미 카드 상단에서 보여주므로 문서 pill까지 전체 경로를 반복하면 정보 밀도가 과해진다.
- 기능별 spec 분리는 앞으로의 작업 방식에 영향을 주는 결정이므로 ADR로 남겨야 한다.
- 검토 필요 기능 안에서도 모든 문서가 검토 대상은 아니므로, 실제 검토가 필요한 문서만 색으로 강조해야 한다.
- 작업 화면에서는 기능과 태스크의 관계를 먼저 읽어야 하므로, 기능 노드의 보조 정보와 하단 고정 상세 리스트를 줄여야 한다.
- 기능과 태스크는 일렬 목록이 아니라 하나의 기능에서 여러 태스크로 분기되는 관계로 보여야 한다.
- 향후 노드 드래그나 동적 배치를 고려하면 CSS pseudo 선보다 SVG 연결선이 확장에 적합하다.
- 테스트/로그/ADR 기록은 계속 누적될 수 있으므로 5개 단위 페이지네이션으로 검토 밀도를 관리해야 한다.
- 정적 내장 데이터만으로는 실제 Markdown 문서 준비 상태와 보드 표시 상태가 어긋날 수 있으므로 상태 동기화 계약이 필요하다.
- 상태 파일 기반 표시가 시작되어야 이후 Codex 작업 요청과 실제 문서 상태를 같은 데이터 기준으로 연결할 수 있다.
